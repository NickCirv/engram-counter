# engram-counter — methodology

[Overview](../README.md) · [Source evidence](RESEARCH.md)

This document describes the computation in revision `c95e418caade2e3ee04695a3cd2e3519520a9dfa`. It replaces unsupported certification and savings claims with the boundaries visible in the implementation. No audit was executed for this documentation rewrite.

## Measurement inputs

Provide baseline and active JSONL logs representing comparable runs. Each record needs a stable `query_id` and the token fields expected by the [parser](https://github.com/NickCirv/engram-counter/blob/c95e418caade2e3ee04695a3cd2e3519520a9dfa/src/parser.ts). The workload label lets the counter check composition; it does not independently verify that two tasks are equivalent. Follow the rewritten [Anthropic](log-conversion/anthropic.md) and [OpenAI](log-conversion/openai.md) conversion guides and inspect the resulting rows against the current parser before measuring.

Choose query identifiers before collecting the two runs. Record dataset, model configuration, task acceptance criteria, collection window and exclusions outside the counter. Keep raw logs and their provenance so missing or altered records can be investigated.

## Computation

The CLI parses both files, joins records by `query_id`, aggregates token differences for matched pairs and calculates workload-fingerprint consistency. It records unmatched counts and warnings instead of silently presenting a perfect match. The [counter](https://github.com/NickCirv/engram-counter/blob/c95e418caade2e3ee04695a3cd2e3519520a9dfa/src/counter.ts), [parser](https://github.com/NickCirv/engram-counter/blob/c95e418caade2e3ee04695a3cd2e3519520a9dfa/src/parser.ts) and [CLI](https://github.com/NickCirv/engram-counter/blob/c95e418caade2e3ee04695a3cd2e3519520a9dfa/src/cli.ts) are the authoritative implementation.

Optional cost accounting uses the bundled pricing table and cache fields. The `--model` flag supplies a default model for rows without one; rows with their own model are priced through the snapshot mapping. The older `--cost-per-million` path applies a single scalar rate and is not interchangeable with cache-aware accounting. Pricing is versioned historical data, not a live quote or an invoice reconciliation.

The metric semantics are now defined explicitly (see the `LogEntry` contract in `src/types.ts`). The four token fields are disjoint categories: `tokens_sent` is uncached input only, `cache_read_tokens` and `cache_creation_tokens` are the cache categories, `tokens_received` is output. Raw token totals sum `tokens_sent + tokens_received` and therefore measure uncached traffic; cache traffic is reported separately as `cache_read_total` / `cache_creation_total` in the cost block. Cache-aware cost prices all four categories, each at its own rate, so with disjoint inputs every token is priced exactly once. An export whose input total includes cached tokens (OpenAI Chat Completions `prompt_tokens` includes `prompt_tokens_details.cached_tokens`) must subtract the cached count before mapping to `tokens_sent`; Anthropic `usage.input_tokens` already excludes the cache categories and maps directly. `tests/provider-examples.test.ts` demonstrates both conversions and shows the exact double-count a cache-inclusive input total produces.

## What the digest establishes

The hash module canonicalizes an audit block and calculates SHA-256. Matching digests support byte-level comparison of that canonical record. The default strict mode also includes a fingerprint of the built distribution and package metadata.

A digest is not a signature, trusted timestamp or proof of authorship. It does not prove that logs are complete, correctly measured or representative; that a task outcome is equivalent; that a binary came from an uncompromised build; or that an organization achieved a particular saving. Package provenance, where actually published and independently verified, is a separate evidence chain. This review did not verify a published artifact or provenance attestation.

## Reproducibility

Use the same source/build, input bytes, labels, options and explicit audit ID when comparing runs. Strict-mode build fingerprints intentionally make the build part of the evidence. `--no-binary-hash` switches to a documented development mode; do not present that output as strict build attribution.

```bash
node bin/engram-counter.js \
  --baseline tests/fixtures/baseline-100q.jsonl \
  --active tests/fixtures/active-100q.jsonl \
  --audit-id local-fixture-review \
  --pretty
```

This is a **source-inspected example, not captured output**. The committed fixtures are synthetic. Their paths were confirmed in the tree, but JSONL contents were excluded from this acquisition filter. No savings percentage or expected digest is restated without executing and verifying that exact fixture/build combination.

When regenerating fixtures, compare newly generated bytes against a separately preserved baseline. Comparing a file with itself cannot establish reproducibility.

## Exit statuses

| Code | Meaning in the inspected CLI |
| --- | --- |
| 0 | Clean audit according to configured mismatch/fingerprint thresholds |
| 5 | Partial audit warning |
| 6 | Failed audit or fail-closed fingerprint/parse path |
| 2 | Invalid invocation |
| 1 | Internal error |

An exit of 0 means the tool accepted the supplied evidence under its rules. It does not certify the experimental design or business conclusion.

## Validation still required

The repository contains tests for parsing, joins, hashing, types, costs, pricing and CLI behavior. None was run for this rewrite. Before relying on a report, validate malformed input, duplicate/missing identifiers, workload mismatch, cache-field interpretation, extreme numeric values and hash reproducibility on the intended runtime. The parser is not a streaming log collection system.
